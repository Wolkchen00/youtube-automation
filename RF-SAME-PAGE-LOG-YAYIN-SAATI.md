- [FIX] Moving `kie-uretim` to `uret` releases the group after production, but default concurrency still retains only one pending job and replaces older pending jobs -> Set `queue: max` on the shared group; `cancel-in-progress: false` alone is insufficient. [GitHub concurrency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
- [CLARIFY] Job-level `concurrency: kie-uretim` does serialize Kie spend repository-wide only if every Kie-consuming operation remains inside a job using that exact group -> Inventory every Kie call and test that no preparation, recovery, or manual path can invoke generation outside the grouped job.

- [FIX] The existing approver cannot serve as the recovery publisher because it calls `_publish_part` without caption, question, first comment, or delivery/coherence context -> Extract one shared publication-and-finalization function and make immediate, delayed, approval, and recovery paths call it with the same immutable payload.
- [KILL] Release creation, remote upload, and Git persistence are not atomic, while `persist_state.sh` only auto-merges `credits_ledger.json`, so cancellation or a rebase conflict after a remote side effect can erase the only local evidence and cause a duplicate -> Write a durable intent before the request and reconcile by deterministic external/request/job ID before every retry.
- [FIX] Publishing a recovered item directly from `uret` bypasses `yayin-<hat>` and can race an older sleeping `yayinla` or a manual run -> All immediate, delayed, manual, and recovery publishing must acquire the same upload-profile concurrency group.
- [FIX] The plan says recovery publishes the pending part and then continues, but `_channel_published_today` is checked only before that recovery -> Return immediately after a recovered publication or rerun the channel-day gate before producing anything else.
- [FIX] Galactic recovery is selected after current-day parity, so a pending `one-variable` item can be ignored on a day that selects `flythrough`, or vice versa -> Scan both slugs for channel-wide pending work before choosing today’s parity.
- [KILL] Fear Slide retains no per-platform durable state, so YouTube success plus Instagram failure blocks all retries, while Instagram success plus YouTube failure causes Instagram/TikTok duplicates on retry -> Persist and reconcile each platform independently before calling `yayinla.py` again.
- [FIX] Fear Slide’s 21:30 gate checks only today’s credit marker and confirmed ledger, so an unconfirmed waiting or scheduled item is treated as “no publication” and may trigger another generation -> Make any pending publication intent suppress new generation and recover that exact master instead.
- [KILL] `scheduled_date` is not a drop-in change because `upload_to_platform` accepts only HTTP 200; an expected HTTP 202 would fall through the retry loop and can submit the same scheduled post three times -> Add an explicit scheduled result type that records `job_id` and never treats queue acceptance as publication. - [FIX] The live duplicate-title gate cannot see a title already queued for later publication, so a lost scheduling commit can enqueue it again -> Reserve normalized titles locally and use deterministic `external_id` plus `Idempotency-Key`, querying scheduled jobs/history before resubmission.

[Upload-Post status API](https://docs.upload-post.com/api/upload-status/)

- [FIX] Logging `hedef_saat` and `gercek_saat` does not test correctness, so a publication hours late still yields `success` -> Fail the proof when confirmed platform publication time is outside an explicit tolerance and test late, canceled, partial, and duplicate cases.
- [FIX] YAML structure tests and mocked single-part tests can pass while provider scheduling, cross-run recovery, or cancellation is broken -> Add contract tests for 202→pending→confirmed, lost-response recovery, persist conflict, cancellation after upload, Galactic cross-parity recovery, and Fear’s 21:30 cron.

### Recommended design

Use `scheduled_date`, but only as a two-phase `schedule → reconcile` state machine—not as a boolean option on the current uploader. It is the only option that actually decouples target time from GitHub cron delay and the six-hour runner cap; Upload-Post stores the media, supports the existing first comment, returns a `job_id`, and exposes status/history reconciliation. Production should run at least one day ahead, persist a deterministic intent before POST, submit the exact existing caption/question/comment payload, and leave the part pending. A lightweight, non-timing-critical reconciler then obtains real platform IDs and invokes the existing registry, lock, advancement, and run-result finalization logic. Never advance or report success on HTTP 202, and never resend an unknown job until status, schedule listing, and history prove it absent or terminally failed.

The waiting-job design preserves synchronous semantics more directly, but it cannot satisfy “regardless of GitHub cron delay” within the measured delays and GitHub’s six-hour ceiling.
